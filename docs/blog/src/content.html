SM120 × 千问3.8

NICKO/SM120 · vLLM · NVFP4

摘要

两批请求的上下文总量几乎相同，为什么解码速度会差这么多？我们在四张 RTX 5090 上运行千问3.8 27B，让模型同时为 32 个请求各生成一个 token。每个请求的上下文都在 8K 左右时，这一步用时 17.9 毫秒；换成一个 128K 的长请求和 31 个 4K 的短请求，就要 28.6 毫秒。多花的时间与工作分配有关：原生注意力内核给每个请求分配相同数量的线程块，分给短请求的线程块已经算完，负责长请求的线程块却还有大量历史数据要读。

预填充时也会出现这样的等待，只是发生在卡与卡之间。长文虽然切成了等长的块，靠后的块要处理的历史却更长，下游 GPU 算完手头的一块，下一块可能还没送到。针对这两种不均衡，我们在卡间采用折返流水线，让同一张卡交替计算模型前后两段；在卡内则按 KV 缓存长度给线程块分工，让长请求得到更多算力。在此基础上，我们又检查了一步解码中各算子之间传递的张量，把三处格式转换并入产生数据的算子，让中间结果在寄存器里就能转成下游需要的格式。[1][8]

01
预填充 / 流水线并行

长上下文预填充的四卡流水线

同样是 2K 个新 token，为什么最后一块算得更久？

以一份 32K 的输入为例，每次处理 2K 个 token，共需处理 16 块。对第一块做全注意力，只需读取这一块里的键和值。轮到最后一块时，虽然新输入还是 2K，但前面 30K 的键和值也要参与计算。线性投影和 MLP 每次处理的数据量大致相同，全注意力的耗时却随输入位置增长。

把这样的输入交给四张卡，耗时差就会变成卡间的等待。常规流水线（CPP）把 64 层模型均分给四张卡。第一块在 GPU0 算完前 16 层就可以交给 GPU1，此时 GPU0 开始算第二块。如果 GPU1 已经算完第一块，而 GPU0 还在算第二块，GPU1 就只能等下一份输入。要估计这段空闲有多长，可以先从单块的计算量算起。

设每块含 C 个新 token，第 j 块之前已有 Hj 个历史 token。由于注意力只能看当前位置及其之前的内容，块内第一个位置要与 Hj + 1 个键做点积，最后一个位置要与 Hj + C 个键做点积。将块内这 C 个位置相加，就得到该块的 Q–K 配对总数 Aj。

Aj=∑i=1C(Hj+i)=CHj+C(C+1)2

在一个流水级内，GDN、线性投影和 MLP 的耗时近似与新输入的长度成正比，可以合写为 aC。设全注意力每处理一对 Q、K 的平均耗时为 b，每块另有固定开销 c，第 j 块的耗时便可写成

tj=aC+bAj+c

后一块比前一块多出 C 个历史位置，每个新位置都要和这些位置计算注意力，合计多出 C² 对 Q、K，耗时差因而约为 bC²。回到四卡流水线，第 s 级要开始算第 j 块，必须等上一级送来输入，也必须等本级算完前一块。两次计算谁结束得晚，就由谁决定本块的起算时间。用 F 记完成时间，有

Fs,j=max(Fs−1,j,Fs,j−1)+tj

这个递推式有个直观的结果。假设各级速度相同，输入块越靠后耗时越长，那么第一级算完所有 N 块需要 Σtj。此时最后一块才刚算完头 16 层，还要在其余三张卡上各算一次。四卡总耗时因而要再加三个 tN；推广到 P 级，就是 Σtj + (P−1)tN。

把 64 层模型折成八段

常规排程的问题出在最后一块：GPU0 做完自己的 16 层就空下来了，其他三张卡却还得依次算完剩下的 48 层。折返流水线（VPP）把每张卡负责的 16 层拆成前后两段，中间穿插其他块的计算。前四段依次放在 GPU0、GPU1、GPU2、GPU3 上，后四段再从 GPU3 往回放。这样，同一块数据走完模型仍须经过全部 64 层，但同一张卡既能算新块的前半程，也能算旧块的后半程。[2][13]

GPU0S0 · L0–7→GPU1S1 · L8–15→GPU2S2 · L16–23→GPU3S3 · L24–31
本地折返 ↓
GPU0S7 · L56–63←GPU1S6 · L48–55←GPU2S5 · L40–47←GPU3S4 · L32–39

看 GPU0 最容易理解这种排程。假设第 0 块已经从 GPU1 返回，第 7 块还在等待进入模型，GPU0 就先给第 0 块算最后八层，再给第 7 块算开头八层。记输入块为 C、流水级为 S，接下来的一段顺序就是 S7(C0) → S0(C7) → S7(C1) → S0(C8)。GPU0 上的两段计算共用一条 CUDA 流。

启动时，第一块还没有返回 GPU0，各张卡先做去程计算。GPU3 算完第一个去程块就能在本地折返，离折返点越远的卡，要先处理的去程块也越多。我们在 GPU0、GPU1、GPU2、GPU3 上分别安排 7、5、3、1 个去程块，随后进入上面的交替顺序。图中选中 C0，就能看到第一块如何经过四张卡，再回到 GPU0。[9]

8K 至 128K 输入的预填充耗时

把四个等长请求放进同一批，折返排程在四种输入长度下都缩短了整批用时。图中两种排程分别采用各自在该长度下最快的配置。32K 时差距最明显，整批用时缩短了 8.55%；继续增加输入长度，折返排程仍然更快，优势却没有继续扩大。[8]

请求数也会影响结果。只提交一个 8K 请求，CPP 用了 304.6 毫秒，VPP 用了 311.0 毫秒。这时流水线中可供交错的块很少，拆细流水级并没有带来收益。

＋实现：单卡上的计算与跨卡传输共享缓冲区、CUDA 流和分段传输实现细节

GPU1 的三条 CUDA 流

以 GPU1 为例，去程的 S1 和回程的 S6 共用一条计算流，另有一条接收流和一条发送流。对同一个块，要先收到输入才能算，有了输出才能发；对不同的块，三条流可以同时工作。GPU1 算当前块的同时，可以从 GPU0 预取后一个块，也可以把先前算好的回程块送往 GPU0。图中实线是数据流向，虚线是主机代理线程发出的控制信号。[9]

接收流有三个缓冲槽，发送流有两个，两个方向的传输共用这组空间。输入块长为 8K 时，隐藏状态和残差合计 160 MiB，五个槽共占 GPU1 上的 800 MiB 显存。一个批次离开本卡以后还要在其他卡上继续计算，本卡的槽却已经可以复用，所以七个在途批次（W=7）无需各占一份槽。去程和回程各有自己的序号和事件，用来标记槽里存的是哪一份数据。

这台机器的跨卡拷贝经由主机内存。每条通信链路在主机上注册一块环形缓冲区，分为八段，每段 16 MiB。160 MiB 的输出需要搬十段，前八段用完缓冲区后，只要接收端已读完第一段，第九段就可以写回第一段的位置。

为了让相邻两段的搬运重叠，每张卡都有一个主机代理线程提前提交拷贝。上游线程把 D2H 拷贝和完成事件放入发送流，随即通过 READY 把这次事件通知下游。下游线程收到通知就提交 H2D 拷贝，并指定它要等待的 D2H 事件。上游拷贝一结束，下游便可接着搬，无需主机再来提交一次。

缓冲槽则按最后一次读取回收。D2H 读完后，上游 GPU 的输出槽可以再写。H2D 读完一段，主机上的这段空间可以再用。下游 GPU 要等整块输入到齐才开始计算，算完该级后才归还接收槽。

02
解码 / 全注意力层

混合长度请求的 KV 分桶

一个 128K 请求与 31 个 4K 请求

回到开头的两批请求。把 32 个请求各自的上下文长度画出来，第一批几乎是一条水平线，每个请求都是 8K；第二批里有一个 128K 的长请求，其余 31 个都是 4K。两批的初始上下文总量只差 256 个 token，恰好是这个注意力内核处理的一个 KV 块。要解释十多毫秒的差距，得看这些块落到了哪些线程块上。

解码采用四卡张量并行（TP4）。在一个全注意力层里，每张卡负责 6 个查询头（Q）和 1 个键值头（KV），每个头有 256 个维度。为了让多个线程块（CTA）并行计算同一请求，原生 FlashInfer XQA 会把历史 KV 切成若干片。对于图 5 中长短混合的这批请求，每个请求都分五片。[6][7]

同样分五片，分到的东西却很不一样。一个 4K 请求总共只有 16 个 KV 块，每片至多 4 块；长请求占 511 块，最重的一片要算 103 块。大部分 CTA 完成时，这几片仍有计算要做。要缩短整批用时，最有用的是把长请求再分给更多 CTA。

按请求分片与跨请求分桶

要让长请求用上更多 CTA，最直接的办法是给它多分几片。FlashAttention-3 就是这么做的：先估算整批的 Q/KV 工作量，再决定每个请求各分几片。无论分多少片，每一片处理的仍然是同一个请求。[4]

腾讯 HPC-Ops 的思路是换一个分配单位：先把整批请求的 KV 块排成一列，再把这列等分给各个 CTA。这样长请求自然占用更多 CTA，而一个短请求的末尾和下一个请求的开头也能分在同一桶里。我们把这套分法接入 SM120 上的 FlashInfer XQA，保留了原有的 NVFP4 缓存读取和注意力计算。[3][15]

从 KV 长度计算分桶大小

具体要给一个 CTA 多少块，可以直接用整批的块数来算。请求 i 的缓存每 256 个 token 占一块，末尾不足 256 个也占一块，记作 ni。把各请求的块数相加，除以可用 CTA 数并向上取整，就得到每桶的容量 B；很短的批次则按每桶至少两块来划分。

B=max(2,⌈∑iniNCTA⌉)

比如图 5 中的长短混合批次总共占 511 + 31 × 16 = 1007 块。按 170 个 CTA 的预算来分，每桶容纳六块。跨过请求边界的桶会产生两个或更多子任务：假如前两块来自 A、后四块来自 B，同一个 CTA 就分别计算 A 的两块和 B 的四块。请求之间只共享执行资源，各自的注意力结果始终分开。[7]

图中选定一个 CTA，可以看到它依次处理哪些请求、每次处理哪一段 KV。对于同一段 KV，内核一边读入新块，一边用在线 softmax 更新统计量；到达这段末尾才写一份局部结果。转到另一个请求时，累加器也随之清零。

相比原生路径，分桶没有减少 QK 或 PV 的运算量。它用更多分片分摊了长请求的计算，也带来了局部结果的写入与归约。两者相抵后能省多少时间，需要看完整模型的一步解码。

等长与混合长度请求的单步解码耗时

对开头那批等长的 8K 请求，两种实现每步都在 17.9 毫秒左右。换成长短混合的 32 个请求，原生路径需要 28.63 毫秒，分桶后只需 18.16 毫秒，已经接近等长批次的水平。把短请求从 31 个减到 8 个，分桶仍有收益，单步耗时从 20.04 毫秒降到 14.37 毫秒。下面的耗时均取自完整模型，每个请求共生成 256 个 token，统计第 17 至 240 个输出位置。[8]

在线服务里，请求随时可能加入或结束，适合上一步的路径未必适合下一步。运行时会根据当前长度分布在 Native、Aligned 和 Persistent 三条路径中选择，把全局分桶留给长短差异明显的批次。用同一组混合请求回放 HTTP 服务，每秒生成的 token 数提高了约 10%–11%。[8]

任务表的生成与跨层复用

一次解码中，同一请求经过不同模型层时，历史长度并不会改变。因此 Assign 内核只需在前向开始时排一次任务，之后形状兼容的全注意力层都能共用。它先对各请求的 KV 块数求前缀和，再找出每桶与各请求的交集。每段交集生成一条 tasks 记录；按桶查这些记录用 buckets，按请求找待合并的结果用 requests。每个桶先占一条记录，桶内每多一道请求边界再加一条，因此 NCTA + batch − 1 项足够。

同一请求的分片如何归约

分片能各算各的，softmax 却需要在一个请求的全部历史上归一化。为此，每段 KV 算完后，每个 Q 头都要留下三个量：局部输出 Oi、片内最高分 mi，以及相对于这个最高分算出的指数和 li。按子任务编号保存它们后，任意 CTA 都可以接手最终归约。

XQA 把这项工作交给最后写完的 CTA。各子任务写完后都更新同一请求的计数器，最后一个到达的 CTA 便可读取全部局部结果，算出完整输出。这样分片与归约可以放在一次内核调用里。[7]

合并时，先找出整个请求的最高分 m，把各片的指数和换算到同一基准。所得的 wi 就是各片在最终输出中应占的权重。

m=maximi,wi=liemi−m,O=∑iwiOi∑iwi

只有一片的请求可以省去归约，直接写出结果。有多片时，计数器的获取/释放语义保证最后一个 CTA 能看到其他 CTA 已经写好的数据，完成归约后再将计数器复位。

当长短请求混合到达时，分桶使输出吞吐提高了 10.41%–11.36%。等长负载的两轮对比只相差 0.03%–0.07%，与上面看到的单步结果一致：没有明显的长度差异时，可供重新分配的工作也很少。

另一种分片调度

FlashAttention-4 在 SM100/SM103 上也能按请求决定分片数，还会结合查询数、头数和可用资源估算任务大小。采用 LPT 排程时，预计耗时较长的任务优先开始，以免它们集中在最后才执行。[5][14]

03
CUDA / 算子融合

解码中的三处算子融合

前一章解决的是同一层里各个 CTA 的分工。沿着一次解码前向看下去，还有一种开销和请求长短无关：一个算子刚把中间结果写回显存，下一个算子又把它读出来，仅仅为了换一种格式。以 MLP 为例，它需要的是 FP4 输入，原生路径却要先保存一份完整的 BF16 归一化结果，再把它读回做量化。

在哪一步量化，决定了这份中间结果要走多远。如果归一化与打包由同一组线程完成，线程之间只需通过共享内存交换归约结果，手中的数值可以留在寄存器里。下面沿 MLP 输入、KV 缓存写入和注意力输出三条路径，分别找出能省掉的那次往返。图中按张量大小计算全局地址空间的读写量；其中命中 L2 的部分无需访问 GDDR7。[16]

3.1 残差相加 + RMSNorm + NVFP4 量化

残差相加之后，数据要分两路走：更新后的残差会在后续层继续使用，需要保留 BF16；归一化结果则只用来生成 MLP 的输入。原生路径把两份结果都写成 BF16，随后量化内核又把第二份完整读回。一行隐藏状态有 5120 个元素，光是这次交接，每个 token 就要写 10 KiB、读 10 KiB。[10]

我们把量化接在归一化之后，让一个 CTA 从头到尾处理一行。10 个 warp 各自求出部分平方和，再由 warp 0 从共享内存中汇总，算出整行共用的归一化系数。每个线程负责的 16 个元素在寄存器中按 BF16 舍入后，就地打包成 NVFP4。这样残差仍按原精度写回，而 MLP 直接拿到排好布局的 FP4 数据和缩放因子，中间的 20 KiB 读写便可以省下。

3.2 QK 归一化 + RoPE + KV 写入

注意力输入端也有类似的分岔。归一化和旋转位置编码（RoPE）完成后，Q 用于当前步的注意力计算，而 K 要与 V 一同存进 NVFP4 缓存，留给后续解码步读取。原生实现把旋转后的 K 先写成 BF16，再交给负责量化和写缓存的内核。[11]

既然旋转后的 K 最终要进缓存，执行旋转的线程就可以顺手完成量化，直接把它写进当前 token 对应的缓存页。V 从投影结果直接量化；Q 和门控值仍按下游需要的 BF16 布局输出。对于一个 256 维的 K 头，这样少写、少读各 512 字节，而后续 XQA 仍可按原布局读取缓存。

3.3 注意力输出 + 门控 + FP8 量化

注意力算完，还要乘以门控值，再把结果转成输出投影所需的 FP8。基线中，vLLM 已通过编译将门控和 FP8 量化合并为一个后处理 kernel；我们进一步把这个后处理并入 XQA 的最终输出阶段，省去一次 kernel 启动，以及 BF16 注意力结果的中间写入和读回。每张卡负责 6 个 Q 头，每头输出 256 个 BF16 值，对应每个 token 省去 3 KiB 写入和 3 KiB 读取。要省去这次交接，关键在于确定哪个 CTA 手里有完整结果。[12]

如果一个请求只分到一片，算完这片的 CTA 就能直接做门控和 FP8 量化。跨片时则要等所有局部结果合并，再由执行最终归约的 CTA 完成同样的操作。这样每张卡每生成一个 token，都少了 3 KiB 的 BF16 写入和 3 KiB 的读回，而且门控始终作用于完整的注意力输出。

算子耗时与完整解码耗时

分别计时，MLP 输入端的残差、归一化和打包合在一起，用时缩短了 33%–39%；注意力输入端省去 K 的交接后，整组算子缩短了 52%–55%。第三项比较完整的 Attention 路径：两侧都包含相同的任务分配与 XQA 计算，基线在 Attention 之后执行已融合的门控与 FP8 后处理，优化版则在 Attention 输出时直接完成。完整路径的耗时下降了 0.7%–1.3%。

部署时关心的是三处一起改完，一步解码实际快了多少。我们在同一条分桶路径上开关融合，比较了 1K、2K 两种上下文，以及 1、8、16、32 四种批量大小。计入词表投影后，完整 GPU 前向的耗时进一步下降了 2.04%–7.18%。[8]

＋实现细节：数据布局、舍入位置与模型接入BF16 舍入 · NVFP4 分组缩放 · 静态 FP8 · HTTP 服务测试实现

输出布局与舍入精度

这三处改动保留了下游算子原有的输入格式：MLP 读取 NVFP4 及其重排后的缩放因子，XQA 读取 BF16 的 Q 和分页的 NVFP4 缓存，输出投影读取按固定比例量化的 E4M3。伪代码中显式写出了 BF16 舍入的位置；原本要靠写回显存完成的舍入，现在可以在寄存器中完成。

三项融合的计算流程 / 伪代码
# ① Residual / Gemma RMSNorm / NVFP4
h = fp32(x) + fp32(residual)
residual_out = bf16(h)
y = bf16(h * rsqrt(mean(h * h) + eps) * (fp32(gamma) + 1))
fp4, scales = pack_nvfp4_native_layout(y)

# ② Attention Front
q = rope(gemma_rmsnorm(q))
k = rope(gemma_rmsnorm(k))
write_bf16_q_and_gate(q, gate)
quantize_and_append_nvfp4(k, v, slot_mapping)

# ③ Attention Final Epilogue
o = bf16(final_attention_output)
g = bf16(sigmoid(fp32(gate)))
gated = bf16(fp32(o) * fp32(g))
write_fp8_e4m3(gated / static_scale)

模型初始化时将这三个内核注册到相应的执行与编译入口。因为各处的输出布局保持一致，原有的 CUDA Graph 和输出投影可以继续使用。

不同负载下的选择

一条请求有多长，只说明了问题的一半。预填充时还得看有多少块可以交错执行：同样是 8K 输入，单请求下常规流水线更快，四请求并发则是折返排程更快。解码时要看长短请求怎样凑在一起：两批 32 个请求的上下文总量接近，等长时换分桶几乎没有区别，长短混合时每步却可以省下 10.47 毫秒。

实际选择实现时，可以先看流水线上哪一级在等输入，再看一个全注意力层里最重的 CTA 要读多少 KV。这两处都调匀以后，再沿着前后算子之间的张量查一次：哪些结果确实还要用，哪些只是为了交给下一个算子才写回。对于千问3.8 27B，残差需要留下，而MLP 的归一化结果和旋转后的 K 可以直接打包成 NVFP4，完整的注意力输出也可以在原地完成门控，再以 FP8 交给输出投影。
