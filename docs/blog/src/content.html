千问3.8 27B 在 SM120 上的推理优化

四卡预填充、长短请求混合解码，以及三处 CUDA 算子融合

NICKO/4 × RTX 5090/SM120 · NVFP4
⌘完整源码与实验数据Nicko-F / qwen3.8-sm120-vpp-bucket-attention↗
预填充 · 四个等长请求4.47–8.55%相对 CPP 的耗时降幅 解码 · 一个长请求和 31 个短请求36.55%相对原生解码的单步耗时降幅 算子融合 · 完整解码步2.04–7.18%在 KV 分桶基础上进一步缩短耗时

用四张 RTX 5090 跑千问3.8 27B 时，我们先注意到了预填充流水线里的空档：一张卡还在算，下一张卡已经空下来等它的输出。解码时，一个 128K 请求混在一批 4K 请求里，大部分线程块很快就算完了，整步解码却还得等负责长请求的那几个。算子之间也有开销。前一个刚把中间结果写回全局内存，后一个就得把同一份数据读回来。

我们分别改了这三处。预填充用折返式虚拟流水线（VPP），让同一张卡交替处理新块和旧块。解码借鉴腾讯 HPC-Ops 的做法，按历史 KV 的长度给线程块（CTA）分配工作。最后把三处相邻操作分别融合，让上游算子直接写出下游需要的量化格式。[1]

01▥ → ▥GPU 之间减少流水线空等 02▂ ▆ ▂ → ▄ ▄ ▄SM 之间摊开长请求的计算量 03□ → □ → ▣算子之间少读写一次中间结果

四张卡连接到同一个 NUMA 节点。预填充用四级流水线并行（TP1/PP4），解码用四卡张量并行（TP4）。权重采用模型自带的 NVFP4/FP8 混合精度，KV 缓存用 NVFP4，隐藏状态和残差用 BF16。[8]

01
预填充 / 流水线并行

用四张卡跑折返流水线

块长相同，为什么后面的块算得更慢？

分块预填充把长输入切成若干块，每次处理 C 个新 token。块长相同，线性投影和 MLP 每次的计算量也差不多。全注意力层的计算量却随历史长度增加。第一块只需看块内的 token，越往后，需要读取的历史 KV 越多。

第 j 块开始时，缓存里已有 Hj 个 token。由于使用因果掩码，块内第一个位置能看到 Hj + 1 个位置，最后一个能看到 Hj + C 个。把这 C 项相加，就是该块要算的 Q–K 配对数 Aj。

Aj=∑i=1C(Hj+i)=CHj+C(C+1)2

看单个流水级。GDN、投影和 MLP 的耗时近似与新 token 数成正比，记为 aC。全注意力每处理一对 Q、K 的耗时记为 b，每块还有固定开销 c。三项相加，就是这个流水级处理第 j 块的时间。

tj=aC+bAj+c

块长固定时，相邻两块相差 C 个历史 token，后一个块在同一级上多花约 bC² 的时间。常规流水线并行（CPP）还得等两件事：上一级送来本块的输入，本级算完上一块。两者取较晚的时刻，再加上本块耗时，就得到它在第 s 级的完成时刻。

Fs,j=max(Fs−1,j,Fs,j−1)+tj

假设各级算得一样快，块的耗时逐块增加。P 级流水线处理完 N 块的总时间就是 Σtj + (P−1)tN。第一项是第一级处理所有块的时间。用四张卡时，最后一块离开第一级以后，还要走完剩下的三级，因此总耗时里又多了三个 tN。

每张卡各跑两段模型

我们把 64 层模型切成 8 段，每段 8 层。前四段从 GPU0 排到 GPU3，后四段再从 GPU3 排回 GPU0。这样，每个块都按层号从小到大计算，到 GPU3 时连续算两段，再把结果往回传。[2][13]

GPU0S0 · L0–7→GPU1S1 · L8–15→GPU2S2 · L16–23→GPU3S3 · L24–31
本地折返 ↓
GPU0S7 · L56–63←GPU1S6 · L48–55←GPU2S5 · L40–47←GPU3S4 · L32–39

以 GPU0 为例，它既负责开头的 8 层（S0），也负责末尾的 8 层（S7）。流水线填满后，它的计算顺序是 S7(C0) → S0(C7) → S7(C1) → S0(C8)：刚算完第 0 块的最后 8 层，就接着算第 7 块的头 8 层。旧块的收尾工作因此能穿插在新块的计算之间。

每张卡只用一条计算流，两段模型轮流算，一次调度 8 层。启动时，GPU0 到 GPU3 分别先算 7、5、3、1 个去程块，随后交替处理回程和去程。四张卡可以同时算不同的块。[9]

四个长请求跑下来能快多少？

我们同时提交四个等长请求，从开始计时到四个请求都生成首个 token。每种输入长度分别取 CPP 和 VPP 各自最快的配置，报告三次计时的中位数。每个请求输入 32K 时，四个请求的总耗时从 4.304 秒降到 3.936 秒。把输入长度从 8K 扫到 128K，VPP 缩短了 4.47%–8.55% 的耗时。[8]

如果只有一个 8K 请求，CPP 用 304.6 毫秒，VPP 用 311.0 毫秒，这时 CPP 快了 6.4 毫秒。四个长请求能拆出更多块，GPU 才有足够的去程和回程工作可以交替执行。

＋单卡上的计算与通信怎么重叠？共享缓冲区、CUDA 流和分段传输实现细节

两个虚拟阶段如何共用一张 GPU

在 GPU1 上，S1 和 S6 共用一条计算流。同一块必须先收到输入，算出相应的输出后才能发走。换成三个不同的块，这三件事就能重叠：计算流算当前块，接收流预取下一块，发送流搬走上一块的输出。图中实线是数据流向，虚线是主机代理线程发出的控制信号。[9]

去程和回程共用三个接收槽、两个输出槽。每块有 8K 个 token 时，一份隐藏状态加残差占 160 MiB，五个槽共占 800 MiB。流水线允许最多七个批次同时在途（W=7），但每个槽只需用到最后一次读取结束：发送流读完就能归还输出槽，本级计算读完就能归还接收槽。去程和回程分别记录序号和就绪事件，通过这些信息区分共用缓冲槽里的数据。

跨卡传输要经过主机内存。每条通信链路在主机上注册一块环形缓冲区，分成 8 段，每段 16 MiB。一份 160 MiB 的输出要分 10 次搬。接收端一读完最早的一段，发送端就能复用那块空间。

每张卡有一个主机代理线程。上游算出一段数据后，代理线程把这段数据的 D2H 拷贝和完成事件排入发送流，再通过共享内存发布 READY。下游收到通知，就可以提前把“等待该事件”和 H2D 拷贝排入接收流。这样，上游一拷完，下游的拷贝引擎就能接着搬。

每个事件只管一段依赖。H2D 完成后，主机上的这一段缓冲就能复用。整块输入到齐后，计算流才能开始算。等这个流水级用完输入，接收槽就能留给下一块。

流水线为什么多花 (P−1)tN？

当各级等速、块耗时 tj 单调不减时，由上面的递推式可得 Fs,j = Σk≤jtk + (s−1)tj。对第 s 级来说，前一块算完后，还要等上游 (s−1)(tj−tj−1) 才能收到下一块。固定块长时，这段等待近似恒定。随着上下文增长，最后一块的耗时 tN 越来越长，整条流水线的附加耗时 (P−1)tN 也随之增加。

02
解码 / KV 工作划分

解码：按 KV 长度分配工作

同样生成一个 token，工作量却可能相差几十倍

解码时，每个请求只生成一个新 token，Q 的长度很短，注意力计算的大部分工作都花在读取历史 KV、计算 QK、softmax 和 PV 上。对于同一层、同样大小的注意力头，KV 越长，要读的数据和要算的点积就越多。

本项目使用 Qwen3.8 NVFP4 模型和 TP4。每张卡上的全注意力层分片包含 6 个 Q 头、1 个 KV 头，头维度为 256。原生 FlashInfer XQA 用 Split-KV 把一个请求拆成几份并行计算。如果每个请求分到的份数相同，128K 请求的每一份就比 4K 请求重得多。[6][7]

举个例子。32 个请求分给 170 个 CTA，原生 XQA 给每个请求分五片。负责 128K 请求的最忙 CTA 要处理 103 个 KV 块（tile），每块含 256 个 token；负责 4K 请求的最忙 CTA 只需处理四块。多数 CTA 很快完成，整次注意力计算却还要等少数几个长分片结束。

从按请求拆分，到跨请求均分

FlashAttention-3 的变长 Split-KV 路径已经能按请求长度调整分片数：先统计整个批次的 Q/KV 工作量，估算每个分片应承担多少工作，再为长请求分配更多分片、为短请求分配更少分片。每个分片处理一个请求内的连续 KV 区间，写出局部输出和 LogSumExp，最后由合并内核汇总结果。[4]

FlashAttention-4 的 SM100/SM103 Split-KV 路径也支持逐请求分片配置，同时考虑查询与注意力头的并行度、KV 长度和硬件容量。LPT 等调度策略则进一步调整执行顺序，让较重的任务先运行。这些方法都在减少任务轻重不均造成的空闲，让一个批次的注意力计算充分利用 GPU。[5][14]

腾讯 HPC-Ops 将分配范围扩展到整个批次：先把所有请求的 KV 工作首尾相接，再按 CTA 预算切分。这样，一个 CTA 处理完前一个请求的末尾后，还可以继续处理下一个请求的开头。本项目沿用了这种划分方式：用 HPC-Ops 的全局 KV 分桶方法分配工作，在 SM120 上用 FlashInfer XQA 读取 NVFP4 KV 缓存并计算注意力。[3][15]

R0R0R0 / R1R1

KV 块、子任务、任务桶如何对应

分配从 KV 块（tile）开始，每块最多包含 256 个 token。第 i 个请求的长度除以 256，再向上取整，就是块数 ni。同一请求内的一段连续块组成一个子任务（Task），分给同一 CTA 的所有子任务组成一个任务桶（Bucket）。把全批次的块数相加，除以 CTA 数量并向上取整，就得到每桶的目标块数，最少取两块。

B=max(2,⌈∑iniNCTA⌉)

前面的 B32 批次共有 511 + 31 × 16 = 1007 个 KV 块，算出每桶的目标大小为 6 块。按请求顺序填桶，跨过请求边界时，就在当前桶里新建一个子任务。GPU 上的 Assign 内核每个解码步生成一次分配表，形状兼容的全注意力层复用同一张表。[7]

Compute 阶段启动固定规模的 CTA 网格。每个 CTA 读取自己的任务桶，依次执行其中的子任务。一个子任务连续处理多个 KV 块，用 online softmax 累积计算，结束时写出一份局部结果（Partial）。如果下一个子任务属于另一个请求，CTA 就重新初始化计算状态，再继续执行。

分桶保留了 XQA 的 KV 加载、QK/PV 和 softmax 计算，只重新安排这些计算由谁来做：原生路径给每个请求相同的分片数，全局分桶则尽量让每个 CTA 承担相近的工作量。

长短请求混在一起，收益最明显

在 TP4 模型测试中，每个请求生成 256 个 token，各组统一用第 17 至 240 个输出 token 统计完整模型的单步耗时。9 个请求的长短混合批次（B9）从 20.04 ms 降到 14.37 ms；32 个请求的混合批次（B32）从 28.63 ms 降到 18.16 ms，延迟分别降低 28.28% 和 36.55%。32 个等长请求则都在 17.9 ms 左右。长短请求带来的工作量差距越大，分桶越能缩短等待长分片的时间。[8]

在混合长度请求持续到达的 HTTP 测试中，Bucket 的输出吞吐也比原生路径高约 10%–11%。运行时保留 Native、Aligned 和 Persistent 三种执行路径，根据请求长度分布选择：工作量均匀时走开销较小的路径，长短差异明显时使用全局分桶。[8]

＋实现细节：任务表、逐桶计算与最终归约任务表跨层复用 · 每个子任务一份局部结果 · Last-CTA Merge实现

Assign 建表，Compute 按表执行

Assign 是一个轻量 GPU 内核。它读取各请求的长度，计算 KV 块数的前缀和，再构建三张表：tasks 记录每个子任务处理的请求及 KV 区间，buckets 记录每个 CTA 负责哪些子任务，requests 记录各请求的局部结果从哪里开始、共有多少份。一个桶跨过请求边界时会拆出多个子任务，因此任务表按 NCTA + batch − 1 预留容量。

任务表的地址在 CUDA Graph 捕获前就已固定。每次模型前向计算时，Assign 只更新表内内容；各注意力层绑定自己的 Q、KV 和输出张量，再按同一张表执行。因此，请求长度变化时，只需更新这份小表，就能调整各 CTA 的工作量。

每个子任务写出局部结果，最后完成的 CTA 负责合并

每个子任务只处理请求的一段 KV。对每个 Q 头，它写出归一化后的局部输出 Oi、局部最大值 mi 和指数和 li。这些数据按子任务编号保存在全局内存的临时缓冲区中。本项目的 TP4 配置下，每份局部输出的有效尺寸为 6 × 256。

子任务写完局部结果后，更新所属请求的完成计数器。该请求最后一个子任务所在的 CTA 负责读取全部局部结果、完成归约，并直接写出最终输出。这就是 Last-CTA Merge：复用 XQA 的内核内归约逻辑，在同一次 Compute 内核调用里完成分片计算与合并。[7]

合并时，先取所有局部最大值中的最大值 m，以它为共同基准计算各分片的 softmax 权重，再对局部输出加权平均。

m=maximi,wi=liemi−m,O=∑iwiOi∑iwi

如果一个子任务就能覆盖整个请求，就直接写出最终输出。有多个子任务时，写入局部结果后，通过带获取/释放语义的原子计数确定最后完成者；归约完成后，再复位本轮计数器。分片数、临时缓冲区位置和完成状态都按请求记录。

算子融合：减少中间结果读写

前两章解决的是工作如何分配，接下来要减少计算过程中的数据搬运。低精度 GEMM 和注意力内核要求输入采用特定的量化格式、缩放因子和内存布局。如果上一个内核写出结果时就完成这些转换，就能省掉中间张量的写回、重读，以及单独的内核调用。

Blackwell 的每个 SM 有四个执行分区，各有自己的 warp 调度器、寄存器和执行单元，共用 SM 内的 L1 缓存与共享内存容量。两个内核分别执行时，上一个内核要先将结果写入全局内存，下一个内核再读取，读取时可能命中 L2。融合后，后续计算可以直接使用还在寄存器中的值。[16]

3.1 残差相加 + RMSNorm + NVFP4 量化

进入 MLP 前，要先把输入与残差相加，执行 Gemma RMSNorm，再量化为 NVFP4。原生路径先将归一化结果存成 BF16 张量，量化内核再将它读回。融合内核在寄存器中完成归一化和 BF16 舍入，随后直接生成 FP4 数据及原生布局的缩放因子；更新后的残差仍以 BF16 写出。[10]

内核每次处理隐藏状态的一行，将行归约、分组量化和缩放因子写入放在一起。这里的隐藏维度为 5120，每 16 个元素组成一个 NVFP4 量化组；缩放因子直接按下游 GEMM 所需的 swizzle 布局写出。

3.2 QK 归一化 + RoPE + KV 写入

注意力计算之前，Q 和 K 需要归一化并应用旋转位置编码（RoPE），V 则需要量化后写入缓存。融合内核直接读取 QKV 投影结果，生成 BF16 格式的 Q 和门控张量，同时根据槽位映射（Slot Mapping），将 NVFP4 格式的 K/V 及缩放因子写入分页缓存。[11]

融合内核将两类输出直接写到各自的位置：Q 供注意力内核读取，K/V 进入预先分配好的缓存页。分页方式、字节步长和量化缩放因子的约定均与原生缓存一致，下游 XQA 可以继续读取原有数据结构。

3.3 注意力输出 + 门控 + FP8 量化

注意力计算的最终结果还要乘上 sigmoid(gate)，再量化为输出投影所需的 FP8。我们把门控与量化放进注意力内核最终写出结果的阶段（Epilogue）：完成归一化与分片归约后，直接生成 FP8 输出。[12]

只有一个子任务时，直接在写出结果前执行门控和量化；有多个子任务时，则由 Last-CTA Merge 中负责最终归约的 CTA 执行。这样，每个请求都只在得到最终结果后做一次门控与量化，各分片的 softmax 计算和合并方式保持一致。

单个算子省下的时间，能带来多少整步收益

在独立算子测试中，残差 / RMSNorm / NVFP4 融合使耗时降低约 33%–39%，QK 归一化 / RoPE / KV 写入融合降低约 52%–55%；注意力输出融合在完整 XQA 尾部测试中降低约 0.7%–1.3%。同时启用三项融合后，在批量为 1、8、16、32，上下文为 1K、2K 的测试中，完整 GPU 解码调用的耗时比未融合的同一 Bucket 路径降低 2.04%–7.18%。[8]

＋实现细节：数据布局、舍入位置与模型接入BF16 舍入 · NVFP4 分组缩放 · 静态 FP8 · HTTP 服务测试实现

三个融合算子各自写出什么格式？

三个内核的输出都匹配原有下游接口。NormPack 生成 NVFP4 数据和 swizzle 布局的缩放因子；Front 生成 BF16 Q、BF16 门控张量，以及分页存储的 NVFP4 K/V；Tail 使用静态缩放因子生成 E4M3 FP8。归一化和 softmax 中的关键归约仍使用 FP32，原有流程中转为 BF16 的位置也保持不变，只是在寄存器中完成舍入。

三项融合的计算流程 / 伪代码
# ① Residual / Gemma RMSNorm / NVFP4
h = fp32(x) + fp32(residual)
residual_out = bf16(h)
y = bf16(h * rsqrt(mean(h * h) + eps) * (fp32(gamma) + 1))
fp4, scales = pack_nvfp4_native_layout(y)

# ② Attention Front
q = rope(gemma_rmsnorm(q))
k = rope(gemma_rmsnorm(k))
write_bf16_q_and_gate(q, gate)
quantize_and_append_nvfp4(k, v, slot_mapping)

# ③ Attention Final Epilogue
o = bf16(final_attention_output)
g = bf16(sigmoid(fp32(gate)))
gated = bf16(fp32(o) * fp32(g))
write_fp8_e4m3(gated / static_scale)

启用 Fusion 配置后，模型初始化时会注册相应的执行与编译 Hook，复用已有的 Bucket CUDA Graph 和原生投影算子。融合内核直接生成下游要求的数据布局，因此可以接入原有的模型前向计算流程。

这些优化何时有效

四个 32K 请求一起做预填充时，折返流水线把耗时从 4.30 秒降到 3.94 秒。解码时，一个长请求混在 31 个短请求里，会让多数 CTA 先做完，等待少数 CTA 处理剩余的 KV。分桶把长请求的工作分给更多 CTA 后，单步耗时从 28.63 毫秒降到 18.16 毫秒。在同一条分桶路径上，算子融合又省去了中间结果的写回和重读；在 1K 和 2K 上下文、批量为 1、8、16、32 的测试中，完整 GPU 解码步的耗时又降低了 2.04% 至 7.18%。
