四张 RTX 5090 跑千问3.8 27B：从流水线调度到算子融合

NICKO/SM120 · vLLM · NVFP4

摘要

我们在四张 RTX 5090 上运行千问3.8 27B，分别优化了预填充和解码。预填充采用折返流水线：把 64 层模型分成八段，每张卡交替执行其中两段。四个 32K 请求同时提交，直到全部生成首个 token，耗时由常规流水线的 4.30 秒降至 3.94 秒。

解码时，按各请求的 KV 缓存长度给线程块分配工作。一个 128K 请求与 31 个 4K 请求同时解码，完整模型的单步耗时从 28.63 毫秒降到 18.16 毫秒。在分桶基础上，我们融合了 MLP 输入、KV 写入和注意力输出端的相邻算子。用 1K 和 2K 上下文测试，批量取 1、8、16、32，完整 GPU 解码步的耗时进一步下降了 2.04%–7.18%。[1][8]

01
预填充 / 流水线并行

长上下文预填充的四卡流水线

相同块长下的注意力耗时

实验使用 vLLM，四张卡位于同一个 NUMA 节点。权重沿用检查点的 NVFP4/FP8 配置，KV 缓存用 NVFP4，隐藏状态和残差用 BF16。

预填充采用四级流水线并行（TP1/PP4）。常规流水线（CPP）把 64 层模型均分给四张卡，每张负责连续的 16 层。以 32K 的输入为例，如果每块取 2K 个 token，一条请求会拆成 16 块。第 0 块在 GPU0 算完前 16 层后就送往 GPU1。此时 GPU0 可以开始算第 1 块，两张卡并行处理不同的输入块。

流水线的难点在于，各块的计算时间有差别。记块长为 C，第 j 块之前已有 Hj 个 token。做因果注意力时，块内第一个位置要跟 Hj + 1 个键计算点积，最后一个位置则要跟 Hj + C 个键计算点积。这一块总共要算多少对 Q 和 K，可以直接求和。

Aj=∑i=1C(Hj+i)=CHj+C(C+1)2

用 b 表示每对 Q、K 对应的注意力计算耗时，GDN、线性投影和 MLP 的耗时则近似随本块新增的 token 数增长，合计为 aC。再计入每块的固定开销 c，单个流水级处理第 j 块的时间约为

tj=aC+bAj+c

每往后移一块，历史长度就多出 C，全注意力也多算 C² 对 Q、K。因此块长固定时，相邻两块在同一级上的耗时相差约 bC²。记第 s 级算完第 j 块的时刻为 Fs,j。本块可以开算的时刻，由上一级送达输入和本级算完上一块这两个时刻中较晚的一个决定。

Fs,j=max(Fs−1,j,Fs,j−1)+tj

如果各级算力相同，且每块耗时逐块递增，第一级算完全部 N 块要花 Σtj。最后一块此时刚离开第一级，后面还有 P−1 级，每级都要花 tN。整条流水线的总耗时为 Σtj + (P−1)tN。四卡时，第二项就是三个末块的单级耗时。

把 64 层模型折成八段

折返式虚拟流水线（VPP）把同样的 64 层切成八段，每段八层。一个块从 GPU0 开始，在去程经过 GPU1、GPU2，到 GPU3 算完第 24–31 层。它接着在 GPU3 算第 32–39 层，再按相反的顺序回到 GPU0，算完最后八层。[2][13]

GPU0S0 · L0–7→GPU1S1 · L8–15→GPU2S2 · L16–23→GPU3S3 · L24–31
本地折返 ↓
GPU0S7 · L56–63←GPU1S6 · L48–55←GPU2S5 · L40–47←GPU3S4 · L32–39

这种排法给了 GPU0 两种可以做的工作：给刚进入流水线的块算前八层，或给从 GPU1 返回的块算最后八层。用 C 表示块、S 表示流水级，稳态下 GPU0 的一段执行顺序是 S7(C0) → S0(C7) → S7(C1) → S0(C8)。第 0 块的回程和第 7 块的去程在同一条计算流上交替执行。

要形成这样的交错，四张卡启动时处理的去程块数不同：GPU0 先处理七块，GPU1 五块，GPU2 三块，GPU3 一块。GPU3 可以最早折返，GPU0 要等第一个块经过其余各级再回来。图中可以单独选中 C0，沿四行时间线看它何时换卡、何时折返。[9]

8K 至 128K 输入的预填充耗时

四个等长请求一起提交，以最后一个请求生成首个 token 为计时终点。CPP 和 VPP 分别取各自在该长度下最快的配置，每组计时三次，取中位数。输入为 8K 时，四个请求的耗时从 832.4 毫秒降到 795.2 毫秒；输入为 32K 时，从 4.304 秒降到 3.936 秒。在测试的四种长度中，32K 的相对降幅最大，为 8.55%。[8]

一个 8K 请求的结果则是 CPP 304.6 毫秒，VPP 311.0 毫秒。块数少时，可供交错的去程和回程计算也少。上图的 4.47%–8.55% 对应四个等长请求同时执行。

＋实现：单卡上的计算与跨卡传输共享缓冲区、CUDA 流和分段传输实现细节

GPU1 的三条 CUDA 流

以 GPU1 为例，S1 和 S6 共用一条计算流，另外两条流分别负责收和发。同一个块的计算要等输入到齐，发送要等对应的输出算好。三个不同的块却可以同时占用这三条流：接收后续块的输入、计算当前块、发送先前块的输出。实线标出数据流向，虚线标出主机代理线程控制的操作。[9]

去程和回程复用同一组缓冲区。块长为 8K 时，一份隐藏状态和残差共 160 MiB。GPU1 的三个接收槽和两个输出槽一共占 800 MiB。虽然流水线最多允许七个批次同时在途（W=7），输出槽在 D2H 拷贝结束后就能再写，接收槽在本地计算用完输入后就能再收。两个方向用各自的序号和就绪事件区分批次。

本机跨卡传输经由主机内存。每条链路有一块已注册的环形缓冲区，分为八段，每段 16 MiB。传完 160 MiB 共需十段。等接收端取走第一段，发送端就可以用同一位置存第九段。

每张卡对应一个主机代理线程。上游线程把 D2H 拷贝和完成事件加入发送流，然后发出 READY。下游线程收到 READY，就把等待该事件和 H2D 拷贝一起加入接收流。上游传完这个分段时，下游的拷贝已经排好，可以立即开始。

这些事件决定缓冲区何时可用。H2D 传完一段，主机缓冲区就可以回收这一段。整块接收完毕，计算流才读取输入。对应的流水级算完后，接收槽才可用于下一个块。

解码 / 全注意力层

混合长度请求的 KV 分桶

一个 128K 请求与 31 个 4K 请求

同一批里的 32 个请求，每一步都各生成一个 token。假设其中一个已有 128K 上下文，其余 31 个各有 4K。此时每个请求只有一个新位置需要查询，但长请求要读取的 KV 缓存约为短请求的 32 倍。

本次解码采用四卡张量并行（TP4）。每张卡在全注意力层上负责 6 个 Q 头和 1 个 KV 头，头维度为 256。原生 FlashInfer XQA 使用 Split-KV，把一个请求的历史 KV 分给多个线程块（CTA）并行计算。对于上面这批输入，原生路径给每个请求分五片。[6][7]

图 5 用每个 CTA 分到的 KV 块数表示工作量，每块最多 256 个 token。长请求占 511 块，分五片后，每片最多 103 块；短请求各占 16 块，分五片后，每片最多 4 块。一次注意力计算要等所有分片算完，因此原生路径中，这一批的结束时间取决于长请求的分片何时算完。

按请求分片与跨请求分桶

要减小分片间的差距，FlashAttention-3 的做法是先估算全批次的 Q/KV 工作量，再分别确定每个请求的分片数。长请求可以多分几片，短请求少分几片。每片仍属于同一个请求，写出局部输出和 log-sum-exp，再由合并算子得到完整输出。[4]

FlashAttention-4 在 SM100/SM103 上也支持按请求确定分片数。调度时还会考虑查询数、头数和可用计算资源。对耗时不同的任务，LPT 策略会优先安排预计用时较长的任务。[5][14]

我们采用腾讯 HPC-Ops 的全局分桶算法。先把整批请求的 KV 块连续编号，再按块数分给各个 CTA。一个 CTA 分到的区间可以跨越请求边界。我们在 SM120 上复用了 FlashInfer XQA 的注意力计算和 NVFP4 缓存读取代码，修改了它领取任务的方式。[3][15]

从 KV 长度计算分桶大小

设请求 i 占 ni 个 KV 块，由缓存长度除以 256 并向上取整得到。把全批次的块数除以可用 CTA 数，再向上取整，就是每桶的目标块数 B。实现中每桶至少按两块分配。

B=max(2,⌈∑iniNCTA⌉)

在图 5 的混合批次中，511 + 31 × 16 = 1007 块 KV 分给 170 个 CTA，每桶最多六块。假设一个桶前两块属于请求 A，后四块属于请求 B，它就包含两个子任务。执行该桶的 CTA 分别为 A 和 B 计算局部结果。每一步解码，Assign 内核只建一次分配表，形状相同的全注意力层共用它。[7]

计算内核启动后，每个 CTA 按表依次执行桶内的子任务。对同一请求的一段连续 KV，用在线 softmax 逐块更新统计量，遍历完再写出一份局部结果。遇到下一个子任务时重新初始化累加状态，这样同一 CTA 可以先后计算两个请求的注意力。

原生 XQA 和分桶 XQA 都要读取同一批 KV，计算相同的 QK 和 PV。图 5 展示的是重新分配之后各个 CTA 的工作量；实际耗时还包含写出和合并局部结果的开销。

等长与混合长度请求的单步解码耗时

我们让每个请求生成 256 个 token，用第 17 至 240 个输出 token 统计完整模型的单步耗时。同为 32 个请求，输入全是 8K 时，原生和分桶方案都是约 17.9 毫秒。把其中的输入换成一个 128K 加 31 个 4K，原生需 28.63 毫秒，分桶需 18.16 毫秒，耗时下降 36.55%。另一个较小的批次由一个 128K 加八个 4K 组成，对应耗时为 20.04 和 14.37 毫秒，下降 28.28%。[8]

实际服务会把不同时间到达的请求合并执行，每一步的请求数和上下文长度都可能变化。运行时根据这一批的长度分布选择 Native、Aligned 或 Persistent 路径，负载明显不均时才使用全局分桶。在长短请求持续到达的 HTTP 测试中，这样做使输出吞吐比原生实现提高约 10%–11%。[8]

同一请求的分片如何归约

对一段 KV，每个 Q 头保留三项局部结果：归一化后的输出 Oi、最高注意力分数 mi、以这个最高分为基准的指数和 li。它们按子任务编号写入临时缓冲区。在这组 TP4 配置中，单个子任务的局部输出有 6 × 256 个元素。

每个子任务写完后更新所属请求的计数器。让最后完成的 CTA 读取该请求的全部局部结果并写出最终值，这就是 XQA 的 Last-CTA Merge。分片计算与最终归约都在同一次内核调用中完成。[7]

各分片的 softmax 使用了各自的最大值。合并时取全请求的最大值 m，把各分片的指数和换算到这个共同基准，得到权重 wi，再对局部输出加权平均。

m=maximi,wi=liemi−m,O=∑iwiOi∑iwi

只有一个子任务的请求可以直接写出结果。有多个子任务时，计数器使用获取/释放语义，确保最终归约能读到先前各个 CTA 写出的局部结果。归约结束后，计数器复位。

03
CUDA / 算子融合

解码中的三处算子融合

KV 分桶缩短了长短请求混合时的解码时间。即便请求一样长，解码过程中也有可以省去的读写。以 MLP 的输入为例，归一化算子刚写出一行 BF16 数据，量化算子就要把整行读回来，而 MLP 真正要读的是量化后的 FP4。

在 Blackwell SM 上，同一内核中的线程可以直接使用寄存器里的中间结果，各 warp 之间可以通过共享内存交换部分和。拆成两次内核调用，就要用全局内存把中间结果传给下一次调用。下面按张量大小计算这次写入和重读的字节数；其中有些读写会命中 L2，实际访问 GDDR7 的流量还取决于缓存命中情况。[16]

3.1 残差相加 + RMSNorm + NVFP4 量化

MLP 之前有两个输出要保留：更新后的残差供后续层使用，归一化后的隐藏状态供 MLP 使用。原生实现先做残差加法和 Gemma RMSNorm，把两者都写成 BF16，再由量化算子读取第二份输出。隐藏维度是 5120，因此每个 token 只算这份中间结果，就要写 10 KiB、再读 10 KiB。[10]

融合后，一个 CTA 处理一行隐藏状态。10 个 warp 分别计算平方和，warp 0 从共享内存读取部分和，得到整行的归一化系数。每个线程把手中的 16 个值按 BF16 舍入，随后在寄存器中打包成一组 NVFP4。残差照常以 BF16 写出；MLP 则直接读取 FP4 数据和按 GEMM 布局排列的缩放因子。这样就省去了上面计算的 20 KiB 中间读写。

3.2 QK 归一化 + RoPE + KV 写入

注意力层的输入有两种去向。Q 经过归一化和旋转位置编码（RoPE）后，以 BF16 交给当前解码步的注意力算子。K 也要做归一化和旋转，但要和 V 一起量化成 NVFP4，写入后续各步还会读取的 KV 缓存。原生路径先写出旋转后的 K，另一个算子再读取它并写入缓存。[11]

我们在算完旋转的地方直接量化 K，按照当前 token 分配到的页和槽位写入缓存。V 从投影结果直接量化，Q 和门控值仍按下游所需的 BF16 布局输出。以一个 256 维 K 头为例，这样省去 512 字节的中间写入和 512 字节的重读。缓存页布局与原生 XQA 一致。

3.3 注意力输出 + 门控 + FP8 量化

最后一处融合在注意力输出端。每张卡有 6 个 Q 头，每头输出 256 个 BF16 值，合计每个 token 3 KiB。原生实现先写出这个张量，后续算子再读入，乘上 sigmoid(gate) 并量化为输出投影需要的 FP8。[12]

门控必须作用于完整注意力输出。一个请求只有一个子任务时，在该子任务写出结果前做门控和 FP8 量化；有多个子任务时，则放到最后一个 CTA 合并局部结果之后执行。两种情况都直接写出 FP8，省掉每张卡、每个 token 合计 6 KiB 的 BF16 中间读写。

算子耗时与完整解码耗时

第一处融合将残差相加、RMSNorm 和 NVFP4 量化的合计耗时降低了 33%–39%。第二处将 QK 归一化、RoPE 和 KV 写入的合计耗时降低了 52%–55%。第三处改的是 XQA 最后的门控与写出，按完整 XQA 尾部计时，耗时下降 0.7%–1.3%。

把三处都接入分桶解码后，我们按完整 GPU 前向调用重新计时，包含输出词表投影。上下文取 1K 和 2K，批量分别取 1、8、16、32。在这些组合中，三项融合让耗时比分桶实现再降 2.04%–7.18%。[8]

输出布局与舍入精度

NormPack 写出打包的 NVFP4 值和按 GEMM 要求重排的缩放因子。注意力输入端写出 BF16 的 Q 和门控值，并更新 NVFP4 的 K/V 缓存页。输出端用固定缩放因子写出 E4M3 格式的 FP8。下面的伪代码标出了每次舍入的位置：归一化和 softmax 的关键归约用 FP32，原流程中转为 BF16 的步骤移到寄存器中完成。

三项融合的计算流程 / 伪代码
# ① Residual / Gemma RMSNorm / NVFP4
h = fp32(x) + fp32(residual)
residual_out = bf16(h)
y = bf16(h * rsqrt(mean(h * h) + eps) * (fp32(gamma) + 1))
fp4, scales = pack_nvfp4_native_layout(y)

# ② Attention Front
q = rope(gemma_rmsnorm(q))
k = rope(gemma_rmsnorm(k))
write_bf16_q_and_gate(q, gate)
quantize_and_append_nvfp4(k, v, slot_mapping)

# ③ Attention Final Epilogue
o = bf16(final_attention_output)
g = bf16(sigmoid(fp32(gate)))
gated = bf16(fp32(o) * fp32(g))
write_fp8_e4m3(gated / static_scale)

这三个内核在模型初始化时注册到相应的执行和编译入口。分桶路径使用的 CUDA Graph 和输出投影都可以继续复用。

不同负载下的选择

选择折返流水线时，先看同一时刻有多少块可供交错。四个等长请求同时预填充，8K 到 128K 都测到了收益；只有一个 8K 请求时，常规流水线用时更短。选择解码路径时，除了批量大小，还要看同批请求的 KV 长度。32 个请求全是 8K，分桶前后都是 17.9 毫秒；换成一个 128K 加 31 个 4K，分桶使单步解码缩短了 10.47 毫秒。

算子融合可以单独考察：先根据中间张量的形状找出可省的读写，再测整个解码步。三处融合里，注意力输入端的独立算子降幅最大；部署后的吞吐，还要回到相同的请求序列上比较。
