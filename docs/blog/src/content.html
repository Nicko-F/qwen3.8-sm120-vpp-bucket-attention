从流水线调度到 CUDA 算子融合

让 GPU 之间的流水更紧凑，让 SM 之间的工作更均衡，让 Kernel 之间的数据少走一趟显存。这是一次围绕 Qwen3.8-27B NVFP4 的端到端推理优化实践。

当模型已经能够稳定运行，接下来的问题往往藏在时间线上：一张卡结束了当前 Chunk，下一张卡还在等待输入；多数 CTA 已经退出，最长请求的 Attention 仍在运行；一个 Kernel 刚把结果写回显存，下一个 Kernel 又把它读回来。

这篇文章沿着这些执行边界，介绍三项落在 SM120、NVFP4 和 vLLM 上的优化。Prefill 采用折返式 VPP，在四张卡之间重新安排模型层与 Chunk；Decode 借鉴腾讯 HPC-Ops 的 KV 分桶，把不同长度请求的工作均衡地分配给 CTA；最后用三个融合算子，直接生成下游计算需要的低精度格式。[1]

实验使用四张同 NUMA 的 RTX 5090。Prefill 走 TP1/PP4，Decode 走 TP4；权重沿用检查点的 NVFP4/FP8 配置，KV Cache 使用 NVFP4，Hidden 与 Residual 保持 BF16。我们先从 GPU 之间的流水看起。[8]

01
PREFILL / PIPELINE PARALLELISM

把长上下文的流水折回来

同样大小的 Chunk，后一个往往更贵

Chunked Prefill 把长 Prompt 分成若干段，每段新增 C 个 Token。线性投影和 MLP 看到的输入规模大致相同，Full Attention 看到的历史却在增长：第一个 Chunk 从零开始，后面的 Chunk 还要访问之前积累的 KV。

记第 j 个 Chunk 开始前的历史长度为 Hj。因果 Attention 中，这段 Query 对应的有效 Q–K 配对数是：

Aj = ∑i=1C (Hj + i) = CHj + C(C + 1)2每个新 Query 访问历史 KV，以及当前 Chunk 中已经出现的 Token。

Qwen 的混合结构中，GDN、投影和 MLP 可以归入近似随 C 线性增长的部分，Full Attention 则带入上面的历史项。于是，一个物理 Stage 的耗时可以写成：

tj = aC + b(CHj + C(C + 1)2) + ca：线性计算成本　b：Full Attention 单位成本　c：固定开销

固定 Chunk Size 后，Hj+1 − Hj = C，相邻 Chunk 的成本增量就是 bC²。图上的计算方块因此会从短变长。常规 PP 又要求一个 Chunk 顺序通过所有 Stage，后面的卡只能在前一张卡完成生产之后继续。

Fs,j = max(Fs−1,j, Fs,j−1) + tj一个 Stage 的开始时间，由输入到达和本地上一项计算结束共同决定。

在等速 Stage、Chunk 耗时单调增加的模型里，P 个 Stage 的总完成时间为 Σtj + (P−1)tN。四卡情况下，尾部相当于额外承担三个最长 Chunk 的 Stage 时间。上下文越长，这一段填排开销也越明显。

每张卡放两段模型，让新旧 Chunk 交错经过

VPP 把 64 层划成 8 个 Virtual Stage，每段 8 层，再将层放置折成一个 U 形：GPU0 持有最前和最后两段，GPU1 持有次前和次后两段，GPU3 完成本地折返。一个 Chunk 仍然按照模型层序前进。[2][13]

GPU0S0 · L0–7→GPU1S1 · L8–15→GPU2S2 · L16–23→GPU3S3 · L24–31
本地折返 ↓
GPU0S7 · L56–63←GPU1S6 · L48–55←GPU2S5 · L40–47←GPU3S4 · L32–39

这样一来，一张 GPU 在处理较新 Chunk 的前半程时，也能穿插处理较早 Chunk 的后半程。进入稳态后，GPU0 的顺序形如 S7(C0) → S0(C7) → S7(C1) → S0(C8)。较短历史的 Return 与较长历史的 Forward 交错，原本集中在尾部的工作被提前穿插到流水中。

同时，单次调度的计算粒度从 16 层缩小到 8 层。每张卡保留一条 Compute Stream，按本地顺序串行执行两段模型；不同卡之间继续并行推进。最初的 Forward 预算是 7 / 5 / 3 / 1，随后自然进入 Forward / Return 交错。[9]

从时间线回到四卡实测

完整 Prefill bank 包含四个请求，每个请求生成一个 Token。在 8K–128K 输入范围内，VPP 的最佳配置将 bank 延迟降低了 4.47%–8.55%；32K 输入的耗时从 4.304 秒降到 3.936 秒。[8]

收益来自流水中同时存在的工作。四个请求提供了充足的 Chunk 供交错执行；只有一个 8K 请求时，CPP 和 VPP 分别为 304.6 ms 与 311.0 ms。随着请求和上下文增加，VPP 对填排过程的重新组织开始发挥作用。

计算流串行，输入和输出异步准备

一个 Rank 同时拥有 Forward 与 Return 两段层。计算沿一条主 Stream 排队，D2H 和 H2D 各用一条 Stream。两个方向共用两个 Source Slot 和三个 Receive Slot：上一份输出正在发送时，下一份输出使用另一块 Source；当前输入正在被消费时，另外两块 Receive 可以准备后续输入。[9]

流水窗口 W=7 记录的是模型中同时推进的 Batch。Source 与 Receive Slot 则跟随数据的读写生命周期周转：Source 在 D2H 读完后归还，Receive 在本地 Stage 最后一次消费结束后归还。Forward 和 Return 保留各自的序列号与事件身份，共享实际的数据空间。

跨卡数据经过 GPU 显存 → 注册的 Host Ring → 下游 GPU 显存。RTX 5090 使用 GDDR7 显存。每条边的 Host Ring 有 8 个 16 MiB Segment。一份 160 MiB 的边界数据分成 10 段，接收端读完较早的 Segment 后，发送端就可以循环复用对应位置。

这条路径由每 Rank 的 C++ Progress Thread 推进。生产者记录输出就绪事件，CPU 侧将 D2H 和完成事件排入发送流，并发布共享内存 READY。接收端看到 READY，就把“等待这个 Event，然后 H2D”一起排入接收流。于是，当上游搬运完成，下游的 Copy Engine 已经有下一项工作可以执行。

H2D 的完成事件负责归还 Host Segment；完整输入的接收事件连接 Compute Stream；Stage 结束时记录的 Consumer Event 则归还 Receive Slot。三种完成条件分别对应三段实际使用过程，通信和计算因此能够独立向前推进。

for (batch, stage) in local_stage_order:
    prefetch_ready_inputs()           # 每个方向最多一份未消费预取

在 vLLM 中，Executor 负责提交 Batch 和 Continuation，Worker 根据本地队列选择 Stage，Runner 切换对应的层并绑定输入输出。Stage 可以直接绑定 Source Slot；捕获的计算图若使用独立输出存储，则先复制到 Slot 再发布就绪事件。模型计算和采样沿用 vLLM，通信层负责把相邻 Stage 的数据依赖接起来。这样，VPP 的调度逻辑与 DMA 的执行细节各有清晰的边界。

为什么 PP 的附加项是 (P−1)tN？

假设各 Stage 等速且 tj 单调不减。由递推式可以归纳得到 Fs,j = Σk≤jtk + (s−1)tj。其中，上游输入完成的时间比本地前一项完成时间多出 (s−1)(tj−tj−1)，所以取最大值后得到上述表达式。令 s=P、j=N，便得到总完成时间。

第 s 个 Stage 在相邻 Chunk 间的间隙为 (s−1)(tj−tj−1)。固定 Chunk 时，每步增量接近常数；随着输入增长，最长 Chunk 仍在变长，累计填排项随之增长。VPP 用更细的 Stage 和折返顺序重新安排这些依赖，页面中的时间线按同一个递推原则生成。

02
DECODE / KV WORK PARTITIONING

按 KV 工作量分配 CTA

同样生成一个 Token，工作量却可能相差几十倍

Decode 的 Query 很短：每个请求只推进一个 Token。Attention 的主要工作变成读取历史 KV，再完成 QK、Softmax 和 PV。对同一层、同一 Head 形状，KV 长度就是一个直接的工作量指标。

在当前 Qwen3.8 NVFP4、TP4 的部署中，每张 GPU 的 Full Attention 分片包含 6 个 Q Head、1 个 KV Head，Head Dimension 为 256。原生 FlashInfer XQA 为请求组织 Split-KV 并行工作。面对一个接近 128K 的请求和一批 4K 请求时，按统一 Split 数分配的 CTA 就会出现明显的长短差。[6][7]

用 170 个 CTA 的预算看 B32：每请求约 5 个 Split。长请求有 511 个 256-token Tile，最重的 CTA 需要处理 103 个 Tile；短请求只有 16 个 Tile，最重的分片约为 4 个 Tile。多数 CTA 结束后，Attention 的关键路径留在少数长分片上。

Split-KV 已经提供了答案，区别在工作如何组合

FlashAttention-3 的变长 Split-KV 路径会先统计整个 Batch 的 Q/KV 工作量，估算每份工作的适宜规模，再分别计算各请求的 Split 数。长请求分配更多分片，短请求分配更少。每个分片处理本请求的连续 KV 区间，写出局部输出与 LogSumExp，随后由 Combine Kernel 完成合并。[4]

FlashAttention-4 的 SM100/SM103 Split-KV 路径同样提供逐请求 Split 元数据，将 Query / Head 并行度、KV 长度和硬件容量一起纳入配置。LPT 等调度策略进一步安排工作顺序，把更重的工作提前执行。这些设计都在回答同一个问题：怎样让当前 Batch 的 Attention 工作更充分地利用 GPU。[5][14]

腾讯 HPC-Ops 的做法更直接地面向整个 Batch：把各请求的 KV 工作连成一条轴，再按 CTA 预算切开。一个 Bucket 可以在处理完上一个请求的尾部后，继续处理下一个请求的开头。这里迁移的就是这条路线：借鉴 HPC-Ops 的全局 KV 工作划分，用 FlashInfer XQA 作为 SM120 上的 NVFP4 计算主体。[3][15]

R0R0R0 / R1R1

Tile、Task、Bucket：三个粒度，一条执行路径

当前 XQA 适配以 256 个 KV Token 为一个 Tile。一个 Task 是某个请求的一段连续 Tile；一个 Bucket 收集分配给同一 CTA 的 Task。对请求 i，先计算 ni = ⌈Li/256⌉，再得到每个 Bucket 的预算：

B = max(2, ⌈Σi niNCTA⌉)所有请求的 Tile 依次填入 Bucket，跨越请求边界时建立新的 Task。

在前面的 B32 例子里，总工作量为 511 + 31 × 16 = 1007 个 Tile，Bucket 预算为 6。长请求的工作于是分散到更多 CTA，短请求的边界也能和相邻请求共享一个 Bucket。GPU 上的 Assign Kernel 每个 Decode Step 生成一次任务映射，兼容的 Full Attention 层复用这份映射。[7]

Compute 阶段启动固定规模的 CTA 网格，每个 CTA 读出自己的 Bucket，在内部依次执行 Task。一个 Task 遍历自己覆盖的多个 KV Tile，持续更新 Online Softmax 状态，结束时写出一份 Partial。跨请求切换时，CTA 复用计算资源，为下一份 Task 建立新的状态。

这保留了 XQA 的 KV 加载、QK/PV 和 Softmax 数据通路，同时把工作分配从“每请求固定几份”变为“每 CTA 近似等量”。分桶改变的是全 GPU 的任务组织；Attention 的数值计算仍由成熟的 XQA 内核完成。

长短混合请求中的收益最明显

完整模型的 Decode Step 中，B9 长短混合负载从 20.04 ms 降到 14.37 ms；B32 从 28.63 ms 降到 18.16 ms，对应 28.28% 和 36.55% 的延迟降低。均匀 B32 的两条路径都在 17.9 ms 左右。工作越偏斜，全局分配可收回的尾部时间越多。[8]

同样的优化也进入了服务路径。混合长度 HTTP 到达负载下，Bucket 的输出吞吐相对原生提升约 10%–11%。运行时保留 Native、Aligned 和 Persistent 三种路线，根据请求长度分布选择合适的执行组织：均匀工作沿用轻量路径，明显偏斜时使用全局 Bucket。[8]

Assign 用一个轻量 GPU Kernel 读取各请求的长度，计算 Tile 前缀和，构建三张表：tasks 记录请求内的 KV 区间，buckets 记录 CTA 对应的 Task 范围，requests 记录同一请求的 Partial 起点和数量。跨请求的 Bucket 会产生多份 Task，因此任务表按 NCTA + batch − 1 预留容量。

Partial 按 Task 保存，最后完成者负责合并

每个 Task 对应一段 KV 区间。对每个 Query Head，它写出归一化的局部输出 Oi、局部最大值 mi 和指数和 li。这些量在 Global Scratch 中按 Task Slot 保存；当前 TP4 形状下，局部输出的有效尺寸为 6 × 256。

Task 写完 Partial 后更新请求级完成计数器。该请求最后完成的 Task 所在 CTA 取得归约职责，读取所有 Partial，直接写出最终结果。这个 Merge 复用 XQA 的内核内归约路径，与分片计算处于同一次 Compute Launch。[7]

单一 Task 覆盖整个请求时，可以直接写最终输出。多 Task 路径在完成 Partial 发布后，通过带获取/释放语义的原子计数选择最后完成者，归约结束时完成该轮计数复位。这把分片数量、Scratch 位置和归约生命周期统一在请求身份下。

03
KERNEL FUSION / PRODUCER → CONSUMER

让上游直接产出下游要的数据

调度让计算资源更忙，算子融合则缩短数据到达下一步的路径。在低精度推理里，GEMM 和 Attention 对输入布局、量化值与 Scale 有明确要求。把这些格式直接放进上游的写回阶段，可以同时省下中间 Tensor 的显存往返和独立处理边界。

这里选择三个高频位置：MLP 之前的 Residual / RMSNorm、Attention 之前的 QK / RoPE / KV 写入，以及 Attention 之后的 Gate / FP8。它们围绕同一个原则展开：结果只落一次显存，落下时就是消费者需要的格式。

3.1 Residual + RMSNorm + NVFP4 打包

MLP 之前，先把输入与 Residual 相加，再做 Gemma RMSNorm，最后量化成 NVFP4。常规路径会物化一个归一化后的 BF16 Tensor，随后量化 Kernel 再读入它。融合后，归一化结果在寄存器中完成 BF16 舍入，直接生成 FP4 数据与原生布局的 Scale；更新后的 Residual 仍以 BF16 写出。[10]

这个 Kernel 以一行 Hidden 为单位执行，把行归约、分组量化与 Scale 写入组合起来。Hidden Width 为 5120，每 16 个元素组成一个 NVFP4 量化组；Scale 按下游 GEMM 使用的 Swizzle 布局直接写回。

3.2 QK Norm + RoPE + KV 写入

Attention 的入口也有相似的机会。Q 和 K 经过归一化与旋转位置编码；V 沿量化写入路径前进。融合 Kernel 从 QKV 投影输出出发，直接生成 BF16 Q 与 Gate，同时根据 Slot Mapping 把 NVFP4 K/V 及 Scale 写入分页 Cache。[11]

这里最重要的是写回目的地：Q 对接 Attention 的输入，K/V 对接已经分配好的 Cache Page。原生 Cache 的分页方式、字节步长和量化 Scale 约定被完整保留，下游 XQA 继续读取同一套数据结构。

3.3 Attention 输出 + Gate + FP8 量化

Attention 得到最终结果后，还要乘上 sigmoid(gate)，再量化成输出投影需要的 FP8。我们把这段处理放进最终输出的 Epilogue：在完成 Attention 的归一化与分片归约之后，直接执行 Gate 与 FP8 打包。[12]

单 Task 路径在直接输出时执行这个 Epilogue；多 Task 路径由 Last-CTA Merge 的最终写出者执行。这样，每个请求的最终输出经过一次 Gate 与量化，分片内部仍沿用原来的 Softmax 合并结构。

算子级的节省，进入完整 Decode 调用

直接算子测试中，Residual / Norm / NVFP4 的耗时降低约 33%–39%，QK / RoPE / KV 写入降低约 52%–55%；Attention Tail 在完整 XQA 尾部的收益约为 0.7%–1.3%。三项融合一起启用，在 B1/8/16/32、1K/2K 上下文的完整 GPU Decode 调用中，相对相同 Bucket 路径降低 2.04%–7.18%。[8]

＋展开实现：把数值格式写在数据流里BF16 边界 · NVFP4 分组 Scale · 静态 FP8 · 完整服务测试IMPLEMENTATION

融合的接口，就是消费者的数据格式

三个 Kernel 都沿用现有消费者的输入约定。NormPack 输出 NVFP4 数据和 Swizzled Scale；Front 输出 BF16 Q、BF16 Gate 以及分页的 NVFP4 K/V；Tail 输出静态 Scale 对应的 E4M3 FP8。归一化和 Softmax 的关键归约使用 FP32，原有 BF16 舍入边界在寄存器内保留。

三个融合边界 / 伪代码
# ① Residual / Gemma RMSNorm / NVFP4
h = fp32(x) + fp32(residual)
residual_out = bf16(h)
y = bf16(h * rsqrt(mean(h * h) + eps) * (fp32(gamma) + 1))
fp4, scales = pack_nvfp4_native_layout(y)

# ② Attention Front
q = rope(gemma_rmsnorm(q))
k = rope(gemma_rmsnorm(k))
write_bf16_q_and_gate(q, gate)
quantize_and_append_nvfp4(k, v, slot_mapping)

# ③ Attention Final Epilogue
o = bf16(final_attention_output)
g = bf16(sigmoid(fp32(gate)))
gated = bf16(fp32(o) * fp32(g))
write_fp8_e4m3(gated / static_scale)

Fusion Profile 在模型初始化时安装对应的执行与编译 Hook，沿用已有 Bucket Graph 和原生投影。数据布局在 Kernel 边界上匹配好，模型 Forward 就能把这些 Producer 接到原有 Consumer 上。

PUTTING IT TOGETHER

从“算得快”，到“接得上”

这三项优化发生在不同尺度，却围绕同一个目标。VPP 让跨 GPU 的后续工作更早就绪；KV Bucket 让同一次 Attention 的工作更均匀地落到 CTA；Fusion 让上游输出到位时，已经具备下游需要的布局和精度。

在这个项目里，vLLM 提供模型执行与服务框架，VPP 和 HPC-Ops 提供了值得迁移的调度思路，FlashInfer XQA 提供低精度 Attention 的计算基础。具体的工程工作，是把这些部分接到 SM120 的硬件和 NVFP4 的真实数据通路上，再沿着时间线、任务表与显存读写观察它们的效果。

GPU 之间安排顺序，SM 之间分配工作，Kernel 之间交付数据。推理性能，正是在这些交界处一点点积累起来的。
