Qwen3.8 27B

From pipeline scheduling to CUDA kernel fusion

Keep the pipeline moving across GPUs, balance work across SMs, and avoid extra VRAM round trips between kernels. An end-to-end inference optimization study of Qwen3.8-27B NVFP4.

Once a model runs reliably, the next problems often hide in its timeline: one GPU finishes a chunk while the next still waits for input; most CTAs have exited while attention for the longest request keeps running; one kernel writes a result to VRAM only for the next kernel to read it back.

This article follows those execution boundaries through three optimizations for SM120, NVFP4, and vLLM. Prefill uses folded VPP to rearrange model layers and chunks across four GPUs. Decode adapts Tencent HPC-Ops KV bucketing to balance requests of different lengths across CTAs. Three fused kernels then produce the low-precision formats their downstream consumers require.[1]

The experiments use four RTX 5090 GPUs on the same NUMA node. Prefill uses TP1/PP4; decode uses TP4. We retain the checkpoint's NVFP4/FP8 weight configuration, use NVFP4 for the KV cache, and keep hidden states and residuals in BF16. We start with the pipeline across GPUs.[8]

01
PREFILL / PIPELINE PARALLELISM

Folding the long-context pipeline

Equal-sized chunks do not cost the same

Chunked prefill divides a long prompt into segments, each adding C tokens. Linear projections and MLPs see roughly the same input size, but full attention sees a growing history: the first chunk starts from zero, while later chunks must also access previously accumulated KV.

Let j be the chunk index and Hj its history length at the start. For causal attention, the number of valid Q–K pairs for this chunk is:

Aj = ∑i=1C (Hj + i) = CHj + C(C + 1)2Each new query attends to historical KV and the tokens already present in the current chunk.

In Qwen's hybrid architecture, GDN, projections, and MLPs contribute work approximately linear in C, while full attention adds the history-dependent term above. We can therefore model one physical stage's runtime as:

tj = aC + b(CHj + C(C + 1)2) + ca: linear compute cost　b: cost per full-attention pair　c: fixed overhead

With a fixed chunk size, Hj+1 − Hj = C, so the cost increase between adjacent chunks is bC². Compute blocks in the timeline therefore become longer. Conventional PP also requires each chunk to pass through every stage in order: a downstream GPU can proceed only after its predecessor produces the input.

Fs,j = max(Fs−1,j, Fs,j−1) + tjA stage starts when both its input has arrived and its previous local computation has finished.

In a model with equally fast stages and monotonically increasing chunk costs, the completion time for P stages is Σtj + (P−1)tN. With four GPUs, the tail is equivalent to three additional stage executions of the longest chunk. This fill-and-drain overhead becomes more pronounced as context grows.

Two model segments per GPU, interleaving old and new chunks

VPP divides 64 layers into 8 virtual stages of 8 layers each, then folds their placement into a U shape. GPU0 holds the first and last segments, GPU1 the second and second-to-last, and GPU3 performs the local turnaround. Each chunk still follows the model's layer order.[2][13]

GPU0S0 · L0–7→GPU1S1 · L8–15→GPU2S2 · L16–23→GPU3S3 · L24–31
Local turnaround ↓
GPU0S7 · L56–63←GPU1S6 · L48–55←GPU2S5 · L40–47←GPU3S4 · L32–39

A GPU can now interleave the early layers of a newer chunk with the later layers of an older chunk. In steady state, GPU0 follows a sequence such as S7(C0) → S0(C7) → S7(C1) → S0(C8). Return work with a shorter history alternates with forward work with a longer history, bringing work that would have accumulated at the tail into the active pipeline.

The scheduling unit also shrinks from 16 layers to 8. Each GPU keeps one compute stream and executes its two model segments serially in local order; different GPUs continue in parallel. The initial forward budgets are 7 / 5 / 3 / 1, after which forward and return work naturally alternate.[9]

From modeled timelines to four-GPU measurements

A full prefill bank contains four requests, each generating one token. Across 8K–128K inputs, the best VPP configurations reduce bank latency by 4.47%–8.55%; at 32K, runtime falls from 4.304 s to 3.936 s.[8]

The gain depends on having work in flight. Four requests supply enough chunks to interleave; with only one 8K request, CPP and VPP take 304.6 ms and 311.0 ms, respectively. As the number of requests and context length grow, VPP's reorganization of filling and draining begins to pay off.

Serial compute, asynchronous input and output preparation

Each rank owns both a forward and a return layer segment. Compute queues on one main stream; D2H and H2D each use a separate stream. Both directions share two source slots and three receive slots. While one output is being sent, the next uses the other source slot; while compute consumes one input, the other two receive slots can prepare upcoming inputs.[9]

The pipeline window W=7 tracks batches concurrently advancing through the model. Source and receive slots instead follow data lifetimes: a source slot is released after D2H finishes reading it, and a receive slot after its last local stage consumer finishes. Forward and return keep distinct sequence numbers and event identities while sharing the physical data buffers.

Cross-GPU data travels through GPU VRAM → registered host ring → downstream GPU VRAM. The RTX 5090 uses GDDR7 device memory. Each edge's host ring contains 8 segments of 16 MiB. A 160 MiB stage-boundary payload is split into 10 segments; once the receiver finishes reading an earlier segment, the sender can reuse that ring position.

A C++ progress thread on each rank advances this path. The producer records an output-ready event. The CPU queues D2H and its completion event on the send stream, then publishes READY in shared memory. Upon seeing READY, the receiver queues both an event wait and the following H2D on its receive stream. When the upstream transfer finishes, the downstream copy engine already has work queued.

The H2D completion event releases the host segment; the full-input receive event connects to the compute stream; the consumer event recorded after stage execution releases the receive slot. These three completion conditions match three actual data lifetimes, allowing communication and compute to advance independently.

Execution outline / pseudocode
for (batch, stage) in local_stage_order:
    prefetch_ready_inputs()           # At most one unconsumed prefetch per direction
    input = receive_for(batch, stage)
    output = borrow_source_slot()

    compute.wait(input.receive_done)
    run_stage(input, output)          # Bind the output slot or copy captured outputs into it
    publish_output_events(output)
    record_consumer_done(input)

# The progress thread advances segmented D2H / H2D.
# Host-side events release credits.

In vLLM, the executor submits batches and continuations, the worker chooses stages from its local queue, and the runner selects the corresponding layers and binds their inputs and outputs. Depending on the execution path, producers may bind the source slot as their output or copy captured graph outputs into it before publishing readiness. vLLM retains model computation and sampling; the communication layer connects adjacent stages' data dependencies. VPP scheduling and DMA execution therefore have separate, explicit responsibilities.

Why does PP add (P−1)tN?

Assume equally fast stages and nondecreasing tj. Induction on the recurrence gives Fs,j = Σk≤jtk + (s−1)tj. Upstream input completion exceeds completion of the preceding local item by (s−1)(tj−tj−1), so taking the maximum yields this expression. Setting s=P, j=N gives the total completion time.

The gap between adjacent chunks on stage s is (s−1)(tj−tj−1). For fixed-size chunks, the cost increment is approximately constant. As the input grows, the longest chunk continues to grow, increasing the total fill-and-drain term. VPP rearranges these dependencies through finer stages and a folded order. The page's modeled timelines follow the same dependency recurrence.

02
DECODE / KV WORK PARTITIONING

Assigning CTAs by KV workload

One output token, tens of times more work

Decode queries are short: each request advances by just one token. Attention mainly reads historical KV and performs QK, softmax, and PV. Within the same layer and head shape, KV length is a direct measure of work.

In this Qwen3.8 NVFP4 TP4 deployment, each GPU's full-attention shard has 6 Q heads, 1 KV head, and head dimension 256. Native FlashInfer XQA organizes Split-KV parallelism for requests. When one request approaches 128K and the others are 4K, assigning the same split count to every request creates markedly uneven CTA workloads.[6][7]

Consider B32 with a budget of 170 CTAs: about 5 splits per request. The long request has 511 tiles of 256 tokens, so its heaviest CTA processes 103 tiles. A short request has only 16 tiles, with about 4 in its heaviest split. After most CTAs finish, a few long splits remain on attention's critical path.

Split-KV addresses the same problem, with a different grouping of work

FlashAttention-3's variable-length Split-KV path first totals Q/KV work across the batch, estimates a suitable workload per split, and then computes each request's split count. Long requests receive more splits and short requests fewer. Each split handles a contiguous KV range within one request, writes a partial output and LogSumExp, and is later merged by a combine kernel.[4]

FlashAttention-4's SM100/SM103 Split-KV path also provides per-request split metadata, factoring query/head parallelism, KV length, and hardware capacity into configuration. Scheduling strategies such as LPT further order work so heavier items run earlier. These designs address the same question: how can the current batch's attention workload use the GPU more fully?[5][14]

Tencent HPC-Ops takes a more explicitly batch-wide approach: concatenate requests' KV work onto one axis, then partition it by the CTA budget. After finishing one request's tail, a bucket can continue with the next request's beginning. This is the approach adapted here: use HPC-Ops global KV partitioning with FlashInfer XQA as the NVFP4 compute body on SM120.[3][15]

Tile, task, bucket: three units, one execution path

This XQA adaptation uses 256 KV tokens per tile. A task is a contiguous tile range within one request; a bucket collects the tasks assigned to one CTA. For request i, first compute ni = ⌈Li/256⌉, then derive the budget per bucket:

B = max(2, ⌈Σi niNCTA⌉)Fill buckets with requests' tiles in order, creating a new task at each request boundary.

In the B32 example above, the total workload is 511 + 31 × 16 = 1007 tiles, giving a bucket budget of 6. The long request is spread across more CTAs, and a short request's boundary can share a bucket with its neighbor. A GPU assign kernel generates the mapping once per decode step; compatible full-attention layers reuse it.[7]

Compute launches a fixed-size CTA grid. Each CTA reads its bucket and executes the tasks in sequence. A task iterates over its KV tiles, updates online softmax state, and writes one partial result when done. At a request boundary, the CTA reuses its compute resources and initializes fresh state for the next task.

This preserves XQA's KV loading, QK/PV, and softmax dataflow while shifting from a fixed split count per request to an approximately equal workload per CTA. Bucketing changes work organization across the GPU; XQA's established kernel still performs the attention arithmetic.

The largest gains come from mixed request lengths

In full-model decode steps, the B9 mixed-length workload falls from 20.04 ms to 14.37 ms; B32 falls from 28.63 ms to 18.16 ms, reducing latency by 28.28% and 36.55%, respectively. For uniform B32, both paths take about 17.9 ms. The more skewed the workload, the more tail time global assignment can recover.[8]

The optimization also reaches the serving path. With mixed-length HTTP arrivals, Bucket increases output throughput by about 10%–11% over native. The runtime retains Native, Aligned, and Persistent paths and chooses an execution strategy from the request-length distribution: a lightweight path for uniform work, and global buckets for pronounced skew.[8]

Assign describes the work; Compute consumes it

Assign uses a lightweight GPU kernel to read request lengths, compute tile prefix sums, and build three tables: tasks holds KV ranges within requests, buckets holds each CTA's task range, and requests holds the first partial slot and partial count for each request. A bucket crossing a request boundary creates multiple tasks, so the task table reserves NCTA + batch − 1 entries.

Core assignment / pseudocode
tiles[i] = ceil(kv_length[i] / 256)
budget = max(2, ceil(sum(tiles) / num_ctas))

for request in batch:
    for overlap in intersect(request.tile_range, bucket_ranges):
        tasks.append(Task(request, overlap.begin, overlap.end))
        buckets[overlap.bucket].append(tasks.last)
        requests[request].append(tasks.last)

# Compatible full-attention layers reuse this table within one decode step.
for task in buckets[blockIdx.x]:
    partial = xqa_attention(task)     # Process consecutive KV tiles within the task
    publish_and_maybe_merge(partial)

Shared task-table addresses are fixed before CUDA Graph capture. On each forward pass, Assign updates their contents; each attention layer binds its own Q, KV, and output tensors, then executes the same work mapping. The dynamic behavior shown here lives in this small descriptor table.

One partial per task; the last finisher merges

Each task covers one KV range. For each query head, it writes a normalized partial output Oi, a local maximum mi, and an exponential sum li. Global scratch stores these values by task slot; for the current TP4 shape, the partial output's effective size is 6 × 256.

After publishing its partial, a task updates the request's completion counter. The CTA containing that request's last-finishing task takes responsibility for reduction: it reads all partials and writes the final output directly. This merge reuses XQA's in-kernel reduction path within the same compute launch as split computation.[7]

m = maxi mi, 　wi = liemi−m
O = Σi wiOiΣi wiReweight each split by its softmax mass to recover the output over the full KV range.

If one task covers the entire request, it can write the final output directly. With multiple tasks, acquire/release atomic counting selects the last finisher after partial publication; the counter is reset when reduction completes. Split counts, scratch locations, and the reduction lifecycle are thus all tied to request identity.

03
KERNEL FUSION / PRODUCER → CONSUMER

Let producers emit what consumers need

Scheduling keeps compute resources busy; kernel fusion shortens the path to the next operation. In low-precision inference, GEMM and attention impose specific requirements on input layouts, quantized values, and scales. Producing these formats during the upstream writeback eliminates intermediate-tensor VRAM round trips and separate processing boundaries.

We target three frequent boundaries: residual/RMSNorm before the MLP, QK/RoPE/KV append before attention, and gate/FP8 after attention. All three follow the same principle: write the result once, already in the consumer's required format.

3.1 Residual + RMSNorm + NVFP4 packing

Before the MLP, the input is added to the residual, normalized with Gemma RMSNorm, and quantized to NVFP4. The conventional path materializes a normalized BF16 tensor, which the quantization kernel reads again. The fused path performs the BF16 rounding in registers, directly emits FP4 data and native-layout scales, and still writes the updated residual in BF16.[10]

The kernel operates on one hidden-state row, combining row reduction, group quantization, and scale writes. Hidden width is 5120, with 16 elements per NVFP4 quantization group. Scales are written directly in the swizzled layout required by the downstream GEMM.

3.2 QK Norm + RoPE + KV append

The attention input boundary offers a similar opportunity. Q and K undergo normalization and rotary position encoding; V follows the quantized append path. Starting from the QKV projection output, the fused kernel directly produces BF16 Q and gate tensors, while using slot mapping to write NVFP4 K/V and their scales into the paged cache.[11]

The destination matters: Q feeds attention, while K/V go into already allocated cache pages. Native paging, byte strides, and quantization-scale conventions are preserved, so downstream XQA reads the same data structures.

3.3 Attention output + gate + FP8 quantization

The final attention result must still be multiplied by sigmoid(gate) and quantized to the FP8 format required by the output projection. We move this processing into the final-output epilogue: after attention normalization and split reduction, it applies the gate and packs FP8 directly.[12]

The single-task path runs this epilogue when writing its output directly; the multi-task path runs it in the final writer of last-CTA merge. Each request's final output is gated and quantized once, while splits retain their existing softmax merge structure.

Operator savings inside a full decode call

Direct operator tests reduce residual/Norm/NVFP4 latency by about 33%–39% and QK/RoPE/KV-append latency by about 52%–55%; the attention-tail gain in the complete XQA tail is about 0.7%–1.3%. With all three fusions enabled, full GPU decode calls across B1/8/16/32 and 1K/2K contexts reduce latency over the same Bucket path by 2.04%–7.18%.[8]

The consumer's format defines the fusion interface

All three kernels preserve their existing consumers' input contracts. NormPack emits NVFP4 data and swizzled scales; Front emits BF16 Q, BF16 gate, and paged NVFP4 K/V; Tail emits E4M3 FP8 with a static scale. Key normalization and softmax reductions use FP32, while existing BF16 rounding boundaries are preserved in registers.

Three fusion boundaries / pseudocode
# ① Residual / Gemma RMSNorm / NVFP4
h = fp32(x) + fp32(residual)
residual_out = bf16(h)
y = bf16(h * rsqrt(mean(h * h) + eps) * (fp32(gamma) + 1))
fp4, scales = pack_nvfp4_native_layout(y)

# ② Attention Front
q = rope(gemma_rmsnorm(q))
k = rope(gemma_rmsnorm(k))
write_bf16_q_and_gate(q, gate)
quantize_and_append_nvfp4(k, v, slot_mapping)

# ③ Attention Final Epilogue
o = bf16(final_attention_output)
g = bf16(sigmoid(fp32(gate)))
gated = bf16(fp32(o) * fp32(g))
write_fp8_e4m3(gated / static_scale)

The fusion profile installs execution and compilation hooks during model initialization, reusing the existing Bucket graphs and native projections. Matching layouts at kernel boundaries lets the model forward pass connect these producers to the existing consumers.

PUTTING IT TOGETHER

From fast computation to well-connected execution

These optimizations operate at different scales but share one objective. VPP makes downstream work ready earlier across GPUs. KV Bucket distributes one attention call's work more evenly across CTAs. Fusion makes producer outputs arrive in the layout and precision their consumers require.

In this project, vLLM supplies the model-execution and serving framework; VPP and HPC-Ops supply scheduling ideas worth adapting; and FlashInfer XQA supplies the low-precision attention compute foundation. The engineering work connects these pieces to SM120 hardware and the actual NVFP4 data path, then examines their effects through timelines, task tables, and VRAM reads and writes.

Order work across GPUs, distribute it across SMs, and deliver data between kernels. Inference performance accumulates at these boundaries.
